# PanHub

PanHub is PanCode's canonical home of shareable packs, contributor entry points, and the generated distribution index. One installable unit is a pack.

## Package Kinds

PanHub organizes shareable packs by kind into dedicated directories under `hub/packs/`:

| Kind | Directory | What an author shares | How it is used |
| --- | --- | --- | --- |
| **Skill** | `hub/packs/skills/` | A procedure and supporting knowledge for the agent | `/skill <skill-name>` |
| **Agent** | `hub/packs/agents/` | A worker definition: role, tools, budget, and result contract | `/run <agent-id> <task>` or dispatch |
| **Prompt** | `hub/packs/prompts/` | Reusable task text and parameterized instructions | `/<derived-prompt-name> [arguments]` |
| **Playbook** | `hub/packs/playbooks/` | An executable multi-agent coordination plan the fleet runs | `/fleet run <playbook>` or preview |
| **Plugin** | `hub/packs/plugins/` | Content released together; it never runs code inside PanCode | Inspect contents, invoke member components |
| **Extension** | `hub/packs/extensions/` | A standalone PanCode runtime package | `/ext:<id>:<command>` or `pancode extensions run <id> <command>` |
| **Server** | `hub/packs/servers/` | The seven PanKit tool servers PanCode carries, as core rows rather than contributions | Built in: `pancode mcp list` shows them and `pankit serve <id>` serves one to another MCP host |

## Browsing and Managing Packages

```bash
# Discover packages in the catalog
pancode hub list
pancode hub search <query>

# Install packages
pancode hub install skill:<name> --project
pancode hub install plugin:hpc --project
pancode hub install extension:local-status --user

# Bring a bare SKILL.md directory in: a reviewed text-only copy, or a manifest
# that keeps what it bundles for an ordinary install
pancode hub import <path-or-github-tree-url> --dry-run
pancode hub package <path>

# Bring installed copies up to their catalog rows
pancode hub update --all --dry-run

# Inspect installed packages
pancode hub skills --all --json

# Read every discovered component with its owner, origin and invocation
pancode hub components --json
pancode hub components <query> --kind agent
```

`hub components` reads the same bounded, body-free inventory PanCode reads through `gateway(op="call", capability="pancode_hub", args={})`, so the operator and the model agree about which components exist, who owns them, where they came from and how each one is actually invoked. Both are reads: installation, removal and activation stay operator actions through `hub install` and `/hub`, and `/skill <name>` stays the way a skill is activated.

In an interactive session, `/hub` opens the PanHub browser.

## Using These Packages From Another Agent

The same sources are usable by Claude Code and Codex with no converted copy and no duplicated component body.

```bash
# Claude Code: the repository is a standard marketplace
claude plugin marketplace add PanStudio/pancode
claude plugin install tdd@pancode
claude plugin install pankit@pancode   # six PanKit MCP servers

# Codex: run a PanKit server as a stdio MCP server
codex mcp add node -- npx -y -p @panstudio/pancode pankit serve node

# Codex: the checkout ships no .agents/skills links, so create them. This gives
# every repository the curated skills and the hpc plugin's skills.
mkdir -p ~/.agents/skills
ln -s "$PWD/hub/packs/skills" ~/.agents/skills/pancode
ln -s "$PWD/hub/packs/plugins/hpc/skills" ~/.agents/skills/hpc
```

`.claude-plugin/marketplace.json` is generated by `pnpm run hub:pin` from the pinned packages in `registry.yaml` and verified by `pnpm run hub:check`. It is never edited by hand.

A package is published there only when a peer host would load a real skill surface from it and nothing it would default-scan into a native component. Agent-, prompt- and playbook-only packages, and packages that keep PanCode agents in a top-level `agents/` directory, stay valid first-class library packages with no peer-host projection; `hub:pin` prints which ones and why. See [coding agent interoperability](../docs/guide/interop.md) for what each host actually loads.

## Authoring Templates

Working, valid authoring templates for the five plugin-backed package kinds live in `hub/_authoring/templates/`:

- `hub/_authoring/templates/skill/`: Single skill package with house metadata and triggers.
- `hub/_authoring/templates/agent/`: Standalone agent with strict v1 format, custom audience, and `skills: []`.
- `hub/_authoring/templates/prompt/`: Reusable prompt with path-derived invocation and argument placeholders.
- `hub/_authoring/templates/playbook/`: Multi-agent coordination playbook with a valid DAG and documented prerequisites.
- `hub/_authoring/templates/plugin/`: Plugin demonstrating an agent binding a contained skill, prompts, and assets.

Templates are authoring reference models; they live outside the five catalog kind roots and never enter `hub/index.yaml`.

## Contributing Packages

Plugin-backed packages carry a portable `plugin.json` manifest. Standalone
extensions carry `pancode-extension.yaml` and install through the extension
writer when selected as `kind: extension` in PanHub.
The optional `extensions["dev.pancode"]` metadata declares a PanCode-specific
kind, resource paths and components; conventional plugin packages can expose
`skills/` without it. The key is metadata inside the interoperable manifest,
and does not name a marketplace service or require a directory. Supported
foreign plugin manifests enter through the separate reviewed import route.

A plugin and an extension are separate packages. The plugin is content: a
portable `plugin.json` that installs without running code inside PanCode. The
extension is PanCode code: a `pancode-extension.yaml` with `runtime.api: 2`, its
own digest, state and envelope consent. An extension may name the one plugin it
serves with top-level `plugin: <name>`; that link alone makes `replaces: prompt`
legal for the plugin's own `/<plugin>:<command>` prompt, and the takeover applies
only while the plugin is installed and enabled. The plugin keeps a working
fallback when its extension is absent. An extension root never holds `plugin.json`.

1. **Choose package kind**: Decide whether your contribution is a single-kind package (`skill`, `agent`, `prompt`, `playbook`) exposing exactly one public component, or a composite `plugin` combining multiple components.
2. **Copy authoring template**: Copy from `hub/_authoring/templates/<kind>/` into your authoring tree.
3. **Author resources**:
   - Single-kind packages expose exactly one public resource file under their resource root (`skills`, `agents`, `prompts`, or `playbooks`).
   - Place `README.md` at the package root, outside the resource root, so it is not discovered as a second component.
   - Packages may carry explicitly invoked scripts (e.g. for offline evaluation or verification). Runtime tools and session hooks belong to an extension package.
4. **Validate**:
   ```bash
   pancode hub validate <package-path> --json
   ```
   Validates manifest schema, resource payloads, package reference markers, and loader compatibility in a read-only pass.
5. **Pin and check**:
   ```bash
   pnpm run hub:pin   # regenerates full-tree pins in hub/index.yaml
   pnpm run hub:check # verifies all package bytes against hub/index.yaml
   ```
   For curated skills under `hub/packs/skills/`, maintainers also run:
   ```bash
   pnpm run skills:pin    # updates normalized skill-body provenance in hub/packs/skills/registry.yaml
   pnpm run skills:check  # verifies skill provenance records
   ```
   *Full-tree pins* cover every distributed byte for runtime package integrity; *normalized skill hashes* record advisory provenance for audited instructions.
6. **Try in isolated project**:
   ```bash
   pancode hub register <package-path> --project
   pancode hub install <kind>:<name> --project
   ```
7. **Submit a focused fork PR**: Push to your fork and open the PR against the current version branch (`v` plus the digits of the `package.json` version, such as `v090`), not `main`. See "Submitting Changes" in [CONTRIBUTING.md](../CONTRIBUTING.md).

Built-in agents and baseline playbooks remain product-owned under `src/domains/agents/builtins/` and `src/domains/agents/playbooks/`.
