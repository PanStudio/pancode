# PanHub architecture

PanHub is how PanCode names, pins, installs and trusts packs. This page states the invariants every pack lifecycle keeps and the signed index designed to carry newer indexes to clients between releases (0.9.0 ships no root key, so every client uses the bundled index); the [PanHub guide](../guide/panhub.md) covers commands and operator controls, and [authoring-plugins.md](../guide/authoring-plugins.md) owns the manifest fields.

Discovery, registration and install plans are `discoverHub`, `planHubInstall` and `commitHubInstallPlan` in [hub.ts](../../src/domains/resources/hub.ts); lifecycle plans are `planHubLifecycle` and `applyHubLifecycle` in [hub-actions.ts](../../src/domains/resources/hub-actions.ts); index rows are checked by `parseHubIndexRows` in [catalog.ts](../../src/domains/plugins/catalog.ts); the signed index is `refreshRemoteIndex` in [hub-trust.ts](../../src/domains/resources/hub-trust.ts) over `verifyKeyCertificate` and `verifyIndexStatement` in [hub-signature.ts](../../src/domains/resources/hub-signature.ts); the root key list is `HUB_ROOT_PUBLIC_KEYS` in [hub-keys.ts](../../src/domains/resources/hub-keys.ts); revocation is `revokedHubDigests` in [hub-revocations.ts](../../src/core/hub-revocations.ts); the CLI is `runHubCommand` in [hub.ts](../../src/cli/hub.ts).

PanCode uses **PanHub** for the collection and **pack** for a distributable item. The CLI `pancode hub`, the slash command `/hub`, the PanHub browser and the bundled `hub/index.yaml` describe the same collection.

## Invariants

1. **One identity.** A content pack has a portable root `plugin.json`, one lowercase portable name and one explicit bounded Semantic Version. Its kind is the `kind` of the PanCode namespace, `extensions["dev.pancode"]`, defaulting to `plugin`. Content kinds are `plugin` and `skill`. The third kind, `extension`, has a `pancode-extension.yaml` manifest and its own state (invariant 12). One name owns one installation directory per scope; changing kind requires removal.
2. **One envelope.** Plugins may carry many public components. A standalone skill pack declares exactly one public skill component, exposes exactly that `SKILL.md` in its resource root, and can carry private supporting files (see [package kinds](../guide/authoring-plugins.md#package-kinds)). Authoring templates live in `hub/_authoring/templates/` outside the kind roots so they never enter the index.
3. **One integrity rule.** The pack digest is a SHA-256 over every file, directory and link in sorted relative-path order, framed by entry kind, path and byte length, so it covers manifests, scripts, references, names and empty directories. Symlinks must resolve inside the pack and their target text is part of the digest; hard links, special files and a symlinked pack root are refused. The same digest function frames extensions, so a digest computed by one engine is comparable to the other. Staging and publication recheck the digest. Neither force nor pin silently approves a changed indexed source. Installed drift revokes resource admission. Validation is strictly read-only: it checks manifest schemas, payload contracts (strict v1 agent schemas with custom audience, playbook DAGs, prompt loadability), acyclic pack references (`${component:...}`, `${pluginRoot}`), and environmental prerequisites without modifying source bytes or state.
4. **One durable state.** The plugin engine owns complete packs at user scope (`<configDir>/plugins/<name>/`) and project scope (`<cwd>/.pancode/plugins/<name>/`). Each scope's `plugins/state.json` records kind, source, structured origin, trust, publisher, install time, the verified digest, and the disabled list. Atomic staging, a per-scope mutation lock, preimage checks and recovery copies apply to every kind. There is no PanHub-specific installer or per-kind pin store. Extensions keep the same guarantees in `extensions/state.json` beside their installed packs.
5. **One workspace picture.** Discovery combines the bundled index, the verified remote index, the user and project indexes and an explicitly selected index with installed state. The list and browser show disabled, damaged and shadowed copies. Effective loading uses one precedence rule: valid, compatible copies compete and the project copy wins, so a disabled project copy still suppresses the user copy. An invalid project copy does not hide a valid user copy, and neither does a project copy blocked by workspace trust (invariant 11). Explicit scope always selects exactly one copy.
6. **One dependency rule.** Manifest and index pack requirements agree, are typed, and form a finite acyclic graph. Only enabled, verified packs satisfy dependencies. Install can plan missing dependencies with explicit inclusion; existing inactive dependencies require repair. Disable and remove refuse when an enabled dependent would lose a satisfied requirement. Atomicity is per pack, not a transaction across a dependency graph.
7. **Trust follows origin.** Each install record carries a structured origin and a trust of `trusted` or `foreign`. Origins `local`, `catalog` and `github` install as trusted, except that a row at tier `listed` installs as `foreign`. Origins `interop` (`{host, source: absoluteOriginalPath}`, from `interop adopt`) and `import` (`{transport, format, source}`, from `hub import`) always install as `foreign`. `installHubPackage({kind, sourcePath, scope, origin, trust, ...})` is exported from [index.ts](../../src/domains/plugins/index.ts). Skill and prompt loaders admit a foreign pack only while `integrations.projectResources.trustProjectImports` is true, at either scope, and that setting never activates loose compatibility roots. Generic updates and forced replacement of foreign content refuse until explicit removal and reviewed re-adoption. Pack trust records the origin of a copy and is independent of the operator's consent to a project's install state, which is workspace trust (invariant 11).
8. **Operator authority remains separate from autonomy.** Active resource trees (`.pancode/{skills,plugins,extensions}/` and the same names under `<configDir>`) are operator-owned: model writes, edits and deletes there are refused for the main agent and for workers at autonomy `default`, and reads stay allowed. At `yolo` only the yolo floor holds, which still refuses them under PanCode's own config directory (`pancode-owned-state`) but not in the project's `.pancode/` trees. A model shell call is inspected for the operator CLI. The mutation verbs of `pancode extensions` (`install`, `update`, `remove`, `enable`, `disable`, `pin`) and `interop adopt --yes` are blocked at `default` and admitted at `yolo`. `pancode share import` (without `--dry-run`), `pancode extensions test` and `pancode extensions validate` ask for one-shot operator confirmation in `default`, because an import installs packs from an archive the model may have written and the other two run a pack's own code. Recognized `pancode hub` mutations (`install`, `import`, `update`, `remove`, `enable`, `disable`, `pin`, `register`, `package`, `sync`, `push`, `remote`) ask for one-shot operator confirmation in `default`, which the safety judge never answers, and are admitted in `yolo`, and a headless run denies the ask. Read-only inspection and a `--dry-run` of `install`, `import`, `update`, `enable`, `disable`, `remove` or `package` stay available and never ask, because a dry run writes nothing. `pancode config trust` is blocked at every autonomy level as part of the yolo floor (`trust-authority`), so the model can never grant workspace trust. This is command inspection, not confinement of arbitrary scripts. Runtime offers and the browser commit only through their bound approval paths; the attended install rule is in [PanHub](../guide/panhub.md#attended-install-rule). Source: [protected-artifacts.ts](../../src/domains/safety/protected-artifacts.ts), [skill-authority.ts](../../src/domains/safety/skill-authority.ts), and the `hub-confirm` rule in [policy-engine.ts](../../src/domains/safety/policy-engine.ts).
9. **One inventory, two projections.** `readHubInventory` in [hub-inventory.ts](../../src/domains/resources/hub-inventory.ts) produces the bounded, body-free record of packs, scoped copies and actual components. The CLI reads it for `hub components` and the model reads it through `gateway(op="call", capability="pancode_hub", args={})`; they agree about ownership, runtime name, scope, origin, availability and invocation because they are the same records. The model projection is narrower, not different: it is the model audience, so internal and shadow agents, untrusted, invalid, shadowed and manual-only resources are absent, and it drops absolute component paths. A catalog `provides` hint is projected as its own tagged row that names its installable owner and that member's availability, and it never carries an invocation. Neither projection activates, installs, registers or pins anything, and neither fetches a remote source. A native worker registry has no admitted PanHub projection and receives a clear unavailable read rather than the global inventory.
10. **One lifecycle plan.** Install, update, enable, disable and remove each build one reviewed plan with [hub-actions.ts](../../src/domains/resources/hub-actions.ts), which stages sources and writes nothing. Applying a plan rechecks every reviewed fact inside each scope's lock and refuses a changed fact as `stale_plan`, a held lock as `locked`, and a broken dependent as `dependents` (the apply outcome reports it as `refused`). A later step failing never undoes an earlier committed step. The result reports disk verification, component admission and host refresh as separate facts, and a failed refresh never undoes a committed write. The CLI and the TUI consume the same plan. For an extension step the plan carries the capability envelope read from the staged manifest (invariant 12).
11. **Project copies need workspace consent.** Project pack digest checks prove integrity; workspace trust supplies consent. The `plugins` surface in [workspace-trust.ts](../../src/core/workspace-trust.ts) approves identities from `.pancode/plugins/state.json` for one canonical workspace. An identity includes the pack id, content digest, envelope digest, source, origin, trust flag and plugin kind. It excludes install time and the disabled list. Reinstalling identical content, disabling or removing a pack preserves consent; enabling an unapproved identity or changing an identity requires approval. An unapproved surface contributes no project resources, satisfies no dependency and never suppresses a user copy. An operator project install through the CLI, the PanHub browser or the GUI can approve only the records it wrote when the prior state was absent or trusted; imports, interop adoption and skill install offers do not grant approval. A task worktree that PanCode created can inherit its origin's approval when its enabled identities are covered, or its state is byte-identical to the approved origin. Extensions use the same contract for `extensions/state.json`. [PanHub](../guide/panhub.md#workspace-trust-for-project-packages) describes review and reload commands.
12. **Plugins and extensions are separate packs.** A plugin is content: installing or discovering it runs none of its files, and a script it carries runs only when a tool later runs it like any other file. An extension is code that runs in its own process, with its own manifest, digest, state file and consent. The operator reviews an extension's capability envelope, including the state it keeps and the prompts it takes over, before install and update. The install records the envelope digest, and it must match again when the install is applied and when the extension loads. An extension may name the one plugin it serves with `plugin: <name>`. That link alone makes `replaces: prompt` legal, and the takeover applies only while the plugin is installed and enabled. An extension root never holds `plugin.json`, and installing either pack never installs the other. The plugin's prompts keep a working fallback for when its extension is absent. The envelope, the sandbox and the runtime are in [extensions](../guide/harness-extensions.md); [hub-pairing.ts](../../src/domains/resources/hub-pairing.ts) answers which partner a pack has, so the browser, the plan and the CLI agree.
13. **Lifecycles leave bounded receipts.** Every committed install, update, enable, disable, remove, register, import and share import records a receipt with the operation, the pack kind and id, the version, the content digest, the envelope digest for an extension, the scope, the source and the actor (`operator`, `model-confirmed` or `upgrade`). Only the most recent 512 receipts are kept in `hub-receipts.json` under the state directory, and the operation is also journaled as a `hub.*` record in the process journal (`recordLifecycleReceipt` in [hub-receipts.ts](../../src/core/hub-receipts.ts)). A damaged receipt store never blocks browsing or admission, and a failed receipt write never undoes a committed change. The PanHub detail pane and `/extensions` show a pack's last lifecycle.
14. **One publisher per pack id.** An install record keeps its publisher: the index row's publisher, else the GitHub owner of its source, else `local`. Installing an id that a different publisher holds in either scope is refused as `hub_publisher_collision` before any source is fetched, with or without `--force` (`publisherCollision` in [package-publisher.ts](../../src/core/package-publisher.ts)). The name `pancode` is reserved for first-party rows.
15. **Revocation applies everywhere a digest is checked.** A revoked digest is never offered, never installed, and never loaded, whichever index named it and whether or not the client is online (see [Revocation](#revocation)).

## Index rows

`parseHubIndexRows` reads every index in one of three modes:

- **bundled**, for `hub/index.yaml` in the installed package;
- **remote**, for the verified remote index;
- **operator**, for the user index, the project index and `--from`.

The bundled and remote modes are strict. Every row names a `publisher`, a `tier` (`core`, `verified` or `listed`) and an SPDX `license`, and has exactly one of `sourceUrl` and `source`. A first-party row has a relative `sourceUrl` under `packs/`, publisher `pancode` and tier `core`. A community row has `source: {repo, commit, subdir}` with `repo` a `https://github.com/<owner>/<repo>` URL and a 40-hex `commit`, a publisher other than `pancode`, and a tier other than `core`. A `verified` row's licence must be on the allowlist (MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, MPL-2.0, CC-BY-4.0, CC0-1.0). A row may carry `envelopeDigest` (extensions only) and `mcpDigest`, the review digests computed by [hub-digests.ts](../../src/domains/resources/hub-digests.ts); a row with a tier pins both, and `planHubInstall` recomputes them from the fetched tree and refuses a mismatch. A row that breaks a rule is dropped with a diagnostic.

The operator mode ignores `tier`, honours `publisher`, and also accepts a `file://` source repository, so a private index works offline.

A remote first-party row (a `sourceUrl` under `packs/`) is offered only when the bundled row of the same name carries the same `sha256`, because its files resolve against the installed package; otherwise PanCode keeps the bundled row and says to update PanCode for that pack.

## Marketplace trust

The bundled index is trusted because it ships inside the published npm package. The design for a newer index to reach clients between releases is a chain of two Ed25519 signatures; 0.9.0 ships the verification code but no root key (see below).

### Keys

- **The root key.** Its private half is held offline by the maintainer. Its public half is compiled into PanCode as a base64 raw Ed25519 key in `HUB_ROOT_PUBLIC_KEYS`. The root signs only key certificates, issued with `node scripts/hub-root.mjs certify`.
- **CI signing keys.** A key certificate names the keys allowed to sign the index. The CI key exists only as the `HUB_SIGNING_KEY` secret of the protected `hub-signing` GitHub environment.
- **The key certificate** is tracked at `hub/keys/signing.json` and checked with `node scripts/hub-root.mjs verify --certificate hub/keys/signing.json`.

A key id is the first 16 hex characters of the SHA-256 of the raw 32-byte public key.

**0.9.0 ships no root key.** `HUB_ROOT_PUBLIC_KEYS` is empty and `hub/keys/` holds no certificate, so the `hub index` workflow publishes nothing and no index verifies: `pancode hub refresh` refuses with `no-root-key` before any network request, `hub install`, `hub update` and `hub list` skip their stale-index refresh, and every client uses the bundled index.

### Envelopes

Both signed documents are envelopes:

```json
{ "payloadType": "<type>", "payload": "<base64 UTF-8 JSON>", "signatures": [{ "keyId": "<16 hex>", "sig": "<base64>" }] }
```

A signature covers the bytes `payloadType`, a newline, then the decoded payload. Base64 must be canonical, so two spellings never name the same bytes.

| Document | `payloadType` | Payload |
| --- | --- | --- |
| Key certificate (`signing.json`) | `pancode.hub.keys.v1` | `{sequence, keys: [{keyId, publicKey, notBefore, notAfter}], revoked: [keyId]}` |
| Index statement (`index.envelope.json`) | `pancode.hub.index.v1` | `{sequence, generatedAt, expires, commit, indexPath, indexSha256}` |

### Publication

The `hub index` workflow ([hub-index.yml](https://github.com/PanStudio/pancode/blob/main/.github/workflows/hub-index.yml)) runs on a push to `main` or a version branch that changes `hub/` outside Markdown, once the repository variable `HUB_SIGNING` is `on` (it is off in 0.9.0, which compiles no root key). It treats the checked-out tree as data: it runs `pnpm hub:check`, signs `hub/index.yaml` with `node scripts/hub-sign.mjs sign` (sequence from the run number, expiry 30 days, commit from the push), verifies the result against `hub/keys/signing.json` and the compiled root keys, and uploads the three assets to the `hub-index` GitHub release:

| Asset | Content |
| --- | --- |
| `signing.json` | The key certificate |
| `index.yaml` | The index |
| `index.envelope.json` | The index statement, uploaded last so a client reading mid-upload sees a hash mismatch and refuses |

### What a client accepts

`refreshRemoteIndex` reads `integrations.hub.index` (default `https://github.com/PanStudio/pancode/releases/download/hub-index/`). Blank is `off`. The URL must be `https`, loopback `http` or `file`, with no credentials, query or fragment, and a redirect away from `https` is refused (`bad-url`). With no root key it stops at `no-root-key`. Otherwise it fetches the three assets (at most 4 MiB each, 20 seconds each; a failure is `unreachable`) and accepts them only when all of these hold:

1. The certificate carries at least one valid signature by a compiled root key; signatures by other keys are ignored, so a root rotation can dual-sign (`bad-root-signature`).
2. The certificate sequence is not lower than the one kept (`certificate-rollback`).
3. The statement carries a valid signature by a certified key that the certificate does not revoke, inside that key's `notBefore`/`notAfter` window (`unknown-key`, `revoked-key`, `key-not-valid-now`, `bad-signature`).
4. The statement is well formed: a sequence, a `generatedAt` before `expires`, a 40-hex commit, an `indexPath` and a SHA-256 (`malformed`).
5. `index.yaml` hashes to `indexSha256` (`index-hash-mismatch`).
6. The index sequence is not lower than the one kept (`index-rollback`), and the kept sequence is not reused for different bytes (`sequence-reused`).
7. The statement has not expired (`expired`).
8. `index.yaml` parses as a remote-mode index with a valid `revoked` list (`malformed`).

On acceptance PanCode writes the three assets to `<stateDir>/hub-index/` and then `<stateDir>/hub-trust.json` (version, both sequences, signing key id, commit, `generatedAt`, `expires`, `verifiedAt`, `indexSha256` and the revocations). The index is written before the state that names its digest, so a crash between the two offers no remote rows rather than unverified ones. A refusal writes only `<stateDir>/hub-index/last-refusal.json` and leaves the kept index, sequences and revocations unchanged.

`hub install`, `hub update` and `hub list` refresh first when the last verification or refusal is six hours old or older. Remote rows are offered only while the remote index is on, a verified state exists, the kept `index.yaml` still matches `indexSha256`, and `expires` is in the future. An expired index offers no rows; installed packs keep loading.

### Revocation

A revocation entry is `{sha256, reason, date}`. The maintainer lists revoked digests in `hub/revoked.yaml`; `pnpm hub:pin` copies them into the `revoked` list of `hub/index.yaml`, so they ship in the next release and, once signed, in the remote index. `revokedHubDigests` returns the union of the bundled list and the list kept in `hub-trust.json`, the bundled entry winning when both name a digest; malformed entries are ignored, and reads are cached by file stat. Kept revocations stay in force while offline and after the remote index expires.

The digest is checked at every point a pack can enter or run:

- **Offer.** `discoverHub` drops a row whose `sha256` is revoked, with a `not offered` diagnostic.
- **Install.** `planHubInstall` refuses a revoked digest.
- **Plugin loader.** `scopeEntries` in [state.ts](../../src/domains/plugins/state.ts) checks each installed content pack's recorded digest; a revoked copy is invalid with `pack_revoked: <id> <sha256> revoked <date>: <reason>`, so its skills, prompts, agents, playbooks and MCP servers stop loading on the next resource read.
- **Extension loader.** `installedFromRoot` in [listing.ts](../../src/domains/extensions/listing.ts) checks each installed extension's expected digest; a revoked extension fails content verification with the same message, and the operator runtime retires a running process with `installation-revoked` at its next command or maintenance pass.

Revocation is stronger than takedown: a takedown removes a listing and leaves installed copies working, while a revocation stops every installation from using that digest.

## Review process

[TERMS.md](https://github.com/PanStudio/pancode/blob/main/hub/TERMS.md) states what a listing promises, the licences, the tiers, takedown, revocation and security. A community pack enters as one row file, `hub/community/<publisher>/<name>.yaml`, naming its repository, exact commit, subdirectory, digest, licence and tier; the format and the verified checklist are in [hub/community/README.md](https://github.com/PanStudio/pancode/blob/main/hub/community/README.md).

| Script | What it does |
| --- | --- |
| `pnpm hub:pin` ([pin-hub.ts](https://github.com/PanStudio/pancode/blob/main/scripts/pin-hub.ts)) | Validates every pack under `hub/packs/<kind>/` and the authoring templates; computes full-tree pins and refuses changed bytes under a version the last `v*` tag already shipped; refreshes skill evidence (`hub/packs/skills/registry.yaml`, `skill-marketplace.json`); fetches each community row's exact commit and regenerates its row, keeping the committed row and failing when a fetch fails; writes `hub/index.yaml` with the `revoked` list; regenerates `.claude-plugin/marketplace.json`. |
| `pnpm hub:check` | The same stages as checks, without fetching; fails on any stale pin. Part of `pnpm lint` and the first step of publication. |
| `pnpm hub:review` ([hub-review.ts](https://github.com/PanStudio/pancode/blob/main/scripts/hub-review.ts)) | Run by the hub review workflow on pull requests that touch `hub/community/`, with `--base <ref>` and `--submission` for a fork. A fork may change one row file and nothing else. Each named commit is fetched as untrusted data with hooks off. Schema, path, digest, licence and launcher-pin failures fail the review; growth of an extension envelope and hits from the body scan are reported as findings for the maintainer. |

The review checks that every `uvx` or `npx` launch in a pack's `mcp.json` pins an exact version (`pkg==x.y.z`, `--from pkg==x.y.z` or `pkg@x.y.z`). The pin fixes the launcher's input, not the bytes the package registry later serves.

## Identity at runtime

Pack identity, component identity and invocation identity are distinct. The pack reference is `kind:name`. A component reference such as `${component:agent:researcher}` is local to one pack and resolves a contained file. It does not rename the agent. Prompt invocation names derive from paths beneath the prompt root with directory separators written as colons, agent IDs derive from agent filenames, and playbooks use their authored names. Authors must choose unique runtime names, normally with their pack prefix. Installation does not add an automatic colon namespace to agents or playbooks.

For example, a plugin named `stats` would use `stats-*` agents and playbooks and `/stats:*` prompts. Runtime collisions use each resource loader's documented precedence and diagnostics; the skill and prompt rules are in [extensions-and-sharing.md](../guide/extensions-and-sharing.md#resource-roots-and-precedence).

## Owners and boundaries

`src/domains/plugins` is the internal engine name because it implements the portable manifest, filesystem integrity, installation state and enabled resource roots. [hub.ts](../../src/domains/resources/hub.ts) composes discovery, registration, requirements and install plans. [hub-actions.ts](../../src/domains/resources/hub-actions.ts) owns lifecycle plans, [hub-validation.ts](../../src/domains/resources/hub-validation.ts) owns pack validation, [hub-trust.ts](../../src/domains/resources/hub-trust.ts) owns the remote index, and [import.ts](../../src/domains/interop/import.ts) owns `hub import`. CLI and TUI consume those functions. The resources domain handles loader-specific schemas, trust and activation; it does not establish a second managed pack lifecycle.

Unmanaged local resource files remain discoverable in established PanCode and foreign roots. The worker's bounded raw-skill preparation helper and authoring audits are not PanHub installations. Their normalized skill-body hashes describe activation and provenance evidence, not installable pack integrity. Maintainer `skills:check` validates authored skill metadata and audit records; the release's distribution integrity rule is `hub:check` over full pack trees.

Pack scripts versus extensions: plugins may carry contained scripts for explicit evaluation or verification workflows without registering runtime tools, hooks or session UI. [Extensions](../guide/harness-extensions.md) remain a separate executable integration contract with their own envelope, sandbox and lifecycle. They cannot own domain resource roots.
