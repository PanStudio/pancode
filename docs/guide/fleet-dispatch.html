    Workers and fleets

    Assign focused tasks and combine workers into a workflow.

    Delegate a focused task

    A worker handles a bounded task while PanCode keeps the main conversation. Start with an explicit goal, files it may change, and the checks it should report.

    Shell

    pancode agents
pancode run "Inspect the parser's test coverage and report gaps. Do not edit files." --agent verifier

    Use an agent ID from your installed catalog: coder makes changes, tester adds tests, reviewer judges a diff, and debugger and verifier only check. Add --worktree to /run to give an editing worker its own branch, or --read-only to make sure it changes nothing. A worker's answer stays out of the conversation until you run /fleet share <runId>, or start it with --share.

    In the terminal, /run <agent-id> <task> starts a worker. The same command with a configured ACP peer's id, or acp:<id>, delegates to that peer. The Workers area of /settings chooses worker defaults without changing the chat model.

    Follow the work

    Alt+W opens the Fleet Runs board to inspect active runs. Select a running worker and use the displayed steer or cancel action. In a session with panes, Alt+W opens the workers dock instead, a live dashboard beside the conversation. You can also send an addressed message:

    @<agentId-or-runId-prefix> Focus on empty input and report the existing tests.

    A steering message first reports queued, then received when the worker acknowledges it. Some external runtimes have no live steering channel; the interface identifies that limit. Review each run's recorded result before using its conclusions.

    Permissions, sandbox, and merges

    Native workers run their shell, script, and verification commands in an OS sandbox: bubblewrap on Linux, or an experimental sandbox-exec profile on macOS. With the default safety.sandbox: auto, they run unsandboxed on a host with no sandbox backend; required refuses them instead, and off disables it. safety.sandboxNetwork: true allows network access.

    Your own session's shell commands run in the same kind of sandbox at default and at contained yolo, which is yolo's default. At unconfined yolo they do not, and workers keep theirs. A worker's ordinary asks go to the safety judge by default (fleet.permissions.mode: judge).

    When a worker's task branch would merge with a failing or unrun check, the terminal asks first with a Merge task branch? card showing the branch, changed paths, and the check. The card opens on Keep branch. Headless runs keep the branch, and so do ACP sessions whose client cannot answer questions. pancode fleet land lists the branches finished runs kept, previews one, and lands it.

    Run a playbook when you need one

    Shell

    pancode playbook list
pancode fleet run sdlc --var task="Add empty-input handling to the parser"
pancode fleet status

    For a script, fleet run --output-format json prints one result document. fleet run --detach returns once the fleet is recorded, pancode fleet wait <fleetRootId> prints the result and exits with its code, and pancode fleet list shows this project's fleets.

    A playbook combines workers into a workflow such as a review gate, competing solutions, or a council. The fleet runs it. Copy a built-in playbook with pancode playbook new <name> --from sdlc, check it with pancode playbook validate <name>, and inspect the approval preview before starting. Its steps work and commit in your checkout, so there is nothing to land afterwards. See the playbook tutorial.

    Give workers MCP tools

    A recipe names exact mcp_<id>__<tool> capabilities, and admission refuses an untrusted or stale server. Grant one project server with pancode mcp trust <id>, then check it with pancode mcp test <id>, which launches only a trusted server. Add --network to mcp trust to allow it network inside the worker sandbox.

    Run workers on another machine

    Remote native workers use SSH and need the same PanCode version and the project at the same absolute path on each node. Add a node with pancode fleet nodes add, or in the terminal under /settings fleet, which opens the Workers area.

    A node receives work only after pancode fleet nodes test <id> --record passes for this project; the record lasts one day. Adding a node moves nothing by itself: unpinned work stays local.

    Start locally with one worker. Use the full guide for remote-node configuration, capacity, recipes, and failure recovery.

    When a worker stops or fails

    A worker has no operator watching it, so fleet.permissions.mode decides what happens when it needs an approval. The default, judge, sends a local worker's ordinary request to the main session's safety judge while that session runs at default; elsewhere it denies. A refused shell command goes back to the worker as a tool result, and the third refusal ends the run with exit 3 and outcome permission_required. The reason names every refused command. Under fail, the first refusal ends the run.

    Some failures retry automatically and some never do:

    • A provider 429 retries on another target after at least one second; a 401 or 403 also moves to another target, and a 408 retries.
    • Other provider 4xx errors, cancellation, policy and permission refusals, and deterministic outcomes such as worker_no_work never retry.
    • Every role owes evidence: an explorer what it observed, a builder a change or a stated reason, a checker executed checks, a reviewer cited evidence. A worker that returns without it is retried once on another model.
    • No attempt retries automatically after it ran a state-changing call, or when its records cannot prove the checkout unchanged.
    • Backoff starts at 500 ms, doubles, and stops at 60 seconds.

    A remote node that fails its channel twice in a row is marked offline. Its in-flight runs settle as stalled and retry without that node, and each reroute is recorded on the run. Read the stop reason in Workers or with pancode fleet status before retrying by hand. The dispatch mechanics reference gives the full failure taxonomy and exit codes.
