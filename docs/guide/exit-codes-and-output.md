# Exit Codes and Machine-Readable Output

When you call PanCode from a script or CI job, the exit code and what lands on stdout tell you how the run went. This page lists every exit code, what each command writes to stdout and stderr, where startup flags may go, and the shape of the JSON and NDJSON output that headless runs (`pancode run`) and other commands print.

The contracts come from the CLI sources ([index.ts](../../src/cli/index.ts), [run.ts](../../src/cli/run.ts), [print.ts](../../src/cli/modes/print.ts), [run-json-schema.ts](../../src/cli/modes/run-json-schema.ts)).

## Exit code contract

Interactive sessions, headless main-agent `run`, and `run --agent` exit `128 + signal` on terminating signals (`129` SIGHUP, `130` SIGINT, `143` SIGTERM). `run` interrupted by SIGINT while reading `@file` inputs exits `130` before sending any request; `pancode configure` exits `130` if exited before saving a first target ([configure-import.ts](../../src/cli/configure-import.ts)).

| Code | Meaning | Trigger conditions |
| --- | --- | --- |
| `0` | Success | Clean completion, `--version`, `--help`, `--dry-run`, declined `reset`/`uninstall`, `upgrade` no-op, passing checks/verifies. |
| `1` | Operational failure | Runtime/provider error; Node.js `< 22.19.0` ([index.ts](../../src/cli/index.ts)); `doctor` error findings; `run` stream without response, `stopReason=length` without terminal tool, empty closing message after tool calls, an answer that ends on a tool call written as text (`no_answer`), a final answer that fails `--output-schema` after its repair turn (`schema_mismatch`), a failed or timed-out `--verify` check under `--fail-on-verify` (`verify_failed`), a `partly_done` or `not_done` completion under `--exit-code`, a recorded limitation whose reason is not `no-runner` (`limitation`), unresolved block or a dispatch that started no worker, with no write (`noop` even without `--fail-on-noop`, except `--turn-mode answer\|proposal` which exits `0` and prints `pancode run: answered with <N> blocked call(s): ...` to `stderr`; [headless-run-verdict.ts](../../src/cli/modes/headless-run-verdict.ts)), `--fail-on-noop`, `dispatched_worker_failed`, deterministic dispatched worker failure (`merge_withheld`, `obligation_unmet`, `worker_not_done`, `worker_partial_work`, `assurance_compromised`, `worker_removed_tests`, `information_flow_blocked`; see table below); `run --agent verifier` with `verdict: "fail"`, or any `run --agent` whose sealed result-contract quality is `fail` because a check failed after its last edit (a `"baseline":true` red before any edit stays `0`; a verifier's settled outcome stays `succeeded`, while a builder such as `coder` seals `failed` with `assurance_compromised`); stdout write error other than `EPIPE` (`pancode run: cannot write output: <message>` on `stderr`, [output-guard.ts](../../src/cli/output-guard.ts)); `reset`/`uninstall` keeping an unproven root; lifecycle/telemetry/playbook failures. |
| `2` | Usage / admission / layout refusal | Unknown command/flag, missing positional, invalid startup flag placement (see [Flag positioning](#flag-positioning)), unsupported flag on `run --agent` (see the note under [Dispatched agent output](#dispatched-agent-output-pancode-run---agent)), an `--answers` file that fails validation (stderr names the offending entry), `run` with neither a task nor `-` (`empty_task`), an unknown `run` flag (`unknown_flag`), conflicting flags (`flag_conflict`, such as `--deny-tools` covering every allowed tool), `run --resume` with `--continue`, `--fork` without either, resuming a session another process holds open (`session_live`), an `--output-schema` the host cannot enforce (`schema_unsupported`), a `--task-file` key repeated on the command line or one that needs `--trust-task-file` (`task_authority`), `--sandbox required` on a host without an OS sandbox, `--require-priced` with an unpriced route in reach, an `-o` path that cannot be written, an invalid playbook under `playbook validate` or `fleet run`, `pancode --resume` naming no session or several, `--resume` with `--continue` or either before a subcommand, a `--cwd` the process cannot enter, an explicit `--skill` path that loads no skill, unknown target or recipe, unselectable/non-chat model, multiple usable routes with no default target and no `--target`, single route without model and no `--model`, task piped to bare `pancode` without `PANCODE_INTERACTIVE=1`, `--autonomy yolo` as root outside a container or under `PANCODE_AUTONOMY_CEILING`, newer-home version mismatch without `PANCODE_ALLOW_OLDER=1` (headless/ACP), unsafe `PANCODE_*_DIR` layout, conflicting lifecycle flags (`reset --all` with a level, `upgrade --restart` with `--json` or `--post-install`), or `reset`/`uninstall` non-TTY without `--yes`/`--dry-run`. |
| `3` | Permission refusal / judge streak | Main-agent `run --on-permission fail` met an ask it cannot approve and ended the run there (cause `permission_required`); under the default `deny` the ask is refused and the turn goes on. Dispatched native or Claude SDK worker stopped after 3 `execute`-class policy refusals (`deny`/`judge`/`main` mode) or on first refusal of any class (`fleet.permissions.mode: fail`); `outcomeDetail` starts with `permission_required` ([worker-refusals.ts](../../src/engine/worker-refusals.ts), [worker-escalation.ts](../../src/engine/worker-escalation.ts)). Main-agent `run --autonomy yolo` halted on safety-judge block streak (run record `outcomeDetail: "judge-streak"`, envelope cause `judge_streak`, exits `3`; [autonomy-window.ts](../../src/domains/safety/autonomy-window.ts)): `` pancode run: judge-streak: the safety judge blocked too many calls (<detail>), so yolo ended the run after <N> tool calls, <M> min, <T> cap tokens; review it, then `pancode run --continue "<prompt>"` resumes with a fresh window ``, followed by the open decisions the run leaves for you, where cap tokens count cache reads at one tenth. A parent `run` dispatching a worker that hits `3` reports `dispatched_worker_failed` and exits `1`; `run --agent` passes `0`, `2`, `3`, `4` through and maps other non-zero worker codes to `1` ([run.ts](../../src/cli/run.ts)). |
| `4` | Spend, request, tool-call or autonomous cap | `run --max-requests <N>` or `run --max-tool-calls <N>` reached (causes `max_requests`, `max_tool_calls`). `safety.limits.sessionCostUsd` (default `5` USD, `0` disables) or `run --max-cost-usd <N>` reached (run record `outcomeDetail: "budget_ceiling"`, envelope cause `session_cost_ceiling` or `max_cost_usd`, [budget.ts](../../src/domains/scheduling/budget.ts)): `budget_ceiling: session priced spend $<spent> reached the $<ceiling> ceiling<per-call>; raise safety.limits.sessionCostUsd` or `budget_ceiling: this run's priced spend $<spent> reached its --max-cost-usd $<cap> cap<per-call>`, where `<per-call>` is ` with ~<n> context tokens per call` when request size is known. Spend strings mark estimates as `~$<x> est` and partial unpriced sums as `$<x> +?`; [renderUsd](../../src/core/telemetry/render.ts) uses 2 decimals at `>= $0.01`, 4–8 decimals below `$0.01`, and scientific notation below `$0.00000001`. Unpriced calls are excluded; priced calls missing server usage estimate from request size and streamed output; prior session spend is excluded from `--max-cost-usd`. Interactive sessions show `[budget] Session priced spend <spend> reached.<perCall> Paid requests are paused; raise safety.limits.sessionCostUsd to <n> to resume.` (or `exceeded.`). Main-agent `run --autonomy yolo` hitting `autonomousToolCalls`, `autonomousMinutes`, or `autonomousTokens` exits `4` (run record `outcomeDetail: "autonomous-cap"`, envelope cause `autonomous_cap`, [autonomy-window.ts](../../src/domains/safety/autonomy-window.ts)): `` pancode run: autonomous-cap: yolo paused at the <detail> after <N> tool calls, <M> min, <T> cap tokens; review it, then `pancode run --continue "<prompt>"` resumes with a fresh window ``. |
| `5` | Unscripted question | Main-agent `pancode run --answers <file.yaml>` met a question the file does not script, or whose matching entry chooses an option not on offer: the round is cancelled, the run settles `failed` with `outcomeDetail: "unscripted"`, and stderr reads `pancode run: unscripted question (<header and id, or the question's first line>): <reason>; add an entry for it to <file> and run again` ([run-answers.ts](../../src/cli/run-answers.ts)). See [Script the author with --answers](commands-and-modes.md#script-the-author-with---answers). |
| `75` | Busy or still live (`EX_TEMPFAIL`) | Non-mutating retry signal: `fleet wait --timeout` expired with the fleet still live, `fleet cancel` accepted but still settling, `fleet verify --exit-code` on a pending run, `.install-lock` held in installer, `upgrade` blocked by active `pid@host` processes or update lease, or launcher 120s timeout waiting for concurrent update. |
| `124` | Run timeout | `pancode run --timeout <duration>` or `fleet run --timeout <duration>` elapsed (matching `timeout(1)`; an external SIGTERM still exits `143` with outcome `canceled`). Runs coordinated shutdown, signals running bash process groups, settles `timed_out`/`failed` (or `canceled` before exit `124` under `--agent`, or no run record if fired pre-turn). |
| `141` | Broken stdout pipe (EPIPE / SIGPIPE) | Consumer closed `stdout` (`pancode run ... \| head -1`). Triggers coordinated shutdown, drops later stdout writes, settles run/session, exits `141` ([index.ts](../../src/cli/index.ts)). |

### Worker failure outcomes (exit `1`, no automatic retry)

| Code | Preserved artifact & meaning |
| --- | --- |
| `merge_withheld` | Task worktree branch kept unmerged (e.g., worker self-validation failed, unverified check asked, or diff removed tests); inspect and merge manually ([attempt-land.ts](../../src/domains/dispatch/attempt-land.ts), [backoff.ts](../../src/domains/dispatch/backoff.ts)). |
| `obligation_unmet` | The run left its evidence obligation unmet: a builder executed no tools, or its state-changing calls were refused or denied, or its asks went unanswered, and nothing changed; an explorer reported without reading; a checker claimed a check it never ran; a gate verdict cited none of its evidence packet ([grading.ts](../../src/domains/dispatch/grading.ts)). An empty task worktree is discarded. |
| `worker_not_done` | A builder declared its assignment `partly_done` or `not_done`, recorded a limitation, or asked for wider write roots, and changed nothing. |
| `assurance_compromised` | A builder's own report lists a failing validation, or it claimed a check it never ran; the merge is withheld and the run fails. A check whose latest `verify` receipt says it could not run is not a failing validation. A failing validation's outcome detail reads `failed validation: <checks>, in the worker's own report` (or `, on its final tree`); a claimed check that never ran reads `assurance compromised: <cause>`. |
| `worker_partial_work` | Edit worker modified files but opened its report saying work could not finish; task worktree changes committed unmerged under `partial: <task>` ([merge-gate.ts](../../src/domains/dispatch/merge-gate.ts)). |
| `worker_removed_tests` | Edit directly on checkout (no task worktree) removed existing tests; edits remain on checkout for review ([attempt-verify.ts](../../src/domains/dispatch/attempt-verify.ts)). |
| `information_flow_blocked` | Policy blocked restricted context from reaching the requested destination; change rule/destination and start a new session ([backoff.ts](../../src/domains/dispatch/backoff.ts)). |

A run that left its evidence obligation unmet is the one exception to "no automatic retry": a builder that settles `obligation_unmet` with no tool call over an unchanged tree is retried once on another model, and its idle task worktree is kept for that attempt ([Evidence obligations and the one retry](fleet-dispatch.md#evidence-obligations-and-the-one-retry)).

## `--help` and flag positioning

Subcommand `--help` exits `0` with zero side effects or network probes, writing to `stdout`; `pancode run --help` does so under `--output-format json|stream-json` too ([run-help.ts](../../src/cli/run-help.ts)). `pancode --help` prints the grouped command page and `--help --all` appends every command path. `pancode help --json` prints the command manifest as one JSON document, and `pancode help run --topics` prints the long-form `run` notes ([help-command.ts](../../src/cli/help-command.ts)). An unknown command or flag exits `2`.

### Flag positioning

Startup flag rules ([index.ts](../../src/cli/index.ts), [argv.ts](../../src/cli/argv.ts)); directory overrides use `PANCODE_*_DIR` / `PANCODE_HOME` ([environment-variables.md](environment-variables.md)):

| Flag(s) | Valid position | Refusal message (`stderr`, exit `2`) |
| --- | --- | --- |
| `--version`/`-v`, `--help`/`-h` | Before subcommand (afterwards belongs to subcommand) | Subcommand parser error (e.g. `pancode paths -v` prints `unknown flag: -v`). |
| `--skill`, `--no-skills` | Either before or after `run` (interactive, `run`, `acp`) | Before other subcommands: `<flag> applies only to the interactive session, pancode run, and pancode acp; pancode <cmd> does not honor it.` |
| `--api-key`, `--no-context-files`/`-nc` | Before `run`/`acp`/interactive only | After subcommand: `<arg> is a global option and must come before the subcommand: pancode <usage> <command> ...` (e.g. `pancode run: --api-key is a global option and must come before the subcommand: pancode --api-key <key> run ...`). Before other subcommands: `<flag> applies only to the interactive session, pancode run, and pancode acp; pancode <cmd> does not honor it.` |
| `--autonomy` | Interactive (pre-command) or *after* `run`/`acp` | Before `acp`: `--autonomy before a subcommand applies to the interactive session only; pass it after it: pancode acp --autonomy <level>`. Before any other subcommand: `--autonomy before a subcommand applies to the interactive session only. For a headless turn use: pancode run --autonomy <level> "<task>"` |
| `--allow-tools`, `--deny-tools`, `--delegate-tools` | Interactive (pre-command) or *after* `run`/`acp` | Before `run`/`acp`: `--allow-tools, --deny-tools and --delegate-tools before a subcommand apply to the interactive session only; pass them after it: pancode <run\|acp> --allow-tools <names>`. Before other subcommands: `--allow-tools, --deny-tools and --delegate-tools apply to the interactive session, pancode run, and pancode acp; pancode <cmd> does not honor them.` |
| `--demo`, `--no-demo`, `--session-file` | Interactive only (no subcommand) | `--demo and --no-demo apply to interactive sessions only; start pancode without a subcommand.` / `--session-file applies to the interactive session only; start pancode without a subcommand.` |
| `--resume`/`-r`, `--continue`/`-c` | Interactive (pre-command) or *after* `run` | Before `run`: `--resume and --continue apply to the interactive session only; for a headless turn pass them after run: pancode run --resume <id> or pancode run --continue`. Before any other subcommand: `--resume and --continue apply to the interactive session only; start pancode without a subcommand.` Both together: `--resume and --continue cannot be combined`. |
| `--with-panes` | Interactive only (before command, no subcommand) | Before subcommand: `--with-panes applies only to the interactive session; pancode <cmd> does not honor it.` After subcommand: `--with-panes applies only to the interactive session; start it with pancode --with-panes` |

## Streams and headless `run` behavior

`pancode run` writes only the final answer (or, under `--output-format json|stream-json`, the result envelope or NDJSON frames) to `stdout`; all diagnostics, permission denials, `observed` summaries, `--verify` results, `Recording manifest (relative to PanCode state): <path>` (`--agent --record`), and pre-send attachment interrupts (`pancode run: interrupted while reading file attachments; nothing was sent`, exit `130`) go to `stderr` ([print.ts](../../src/cli/modes/print.ts), [run.ts](../../src/cli/run.ts)). Arguments are validated before any state is read.
- `--output-format text` (the default) ends with one `stderr` line: `pancode run: session <id> · <outcome> · <N> requests · <in>/<out> tokens · <cost or unpriced>`.
- `-o <path>` (`--output-last-message`) writes the final answer to a file when the run exits `0`; with `--output-schema` the file holds the validated JSON.
- Stdin is read only when `-` is passed. For machine-readable output, use `--output-format json` or `--output-format stream-json`.
- Unconfirmed permissions in headless mode return `HEADLESS_PERMISSION_DENIED_REASON` (`pancode run cannot confirm permission requests; rerun interactively to approve this action.`) as a tool error so the model can adapt or call `limitation` ([headless-permission.ts](../../src/core/headless-permission.ts)). `--on-permission fail` ends the run at the first such ask with exit `3` instead.
- Runs that called `>= 1` tool emit one `stderr` line after completion (`headless-observed.ts`):
  `pancode run: observed: <N> tool call(s), <M> refused [· <W> write(s)] [· check(s) passed: <names>] [· check(s) failed: <names>] [· unclassified command(s) failed: <names>] [· <U> unclassified command(s) ran after a standing check] [· no check observed after the last write | no checks declared in the workspace]` (max 3 check names per list; does not alter stdout or exit code). A passing dispatch run record that no later write retired is named among the passed checks as `run <id> agent <agent>`, as on the task board. An unclassified call is one the check classifier (`check-classifier.ts`) reads as neither a check, an inspection nor a mutation, such as `node codemod.mjs` or an MCP tool. A `python`, `node`, `bash` or `sh` call that runs a script by a relative path inside the tree, whose file stem holds `check`, `test` or `verify` (or `checks`, `tests`, `verification`) as a whole word, is a check, such as `python3 -u verify_stencil.py` or `node scripts/test.mjs`. A check written as `<check>; echo "EXIT=$?"` is judged on the status it echoed, not on the exit of `echo`. It neither settles nor clears a standing check, so a passing one is only counted while any check that ran before it still stands, while one that ran and failed is named whether or not a check stands, until a later write; the run receipt's `unclassifiedAfterLastCheck` (count plus up to 5 redacted commands) carries it too. A check chained to an unknown program in one command, such as `cargo build && ./target/debug/app`, reads as mixed: it settles no pass and retires a standing one, so run the check as its own command (known limit).
- `--verify "<cmd>"` runs each check after the turn settles, logs to `stderr`, and reports each check in the `run_end` envelope's `verify.checks` under `--output-format json|stream-json` (plus a `verify` frame under `stream-json`); it does not override the run's exit code unless `--fail-on-verify` is passed, which exits `1` with cause `verify_failed` when a check failed or timed out ([print.ts](../../src/cli/modes/print.ts)).

### Failures before output starts

When a run under `--output-format json|stream-json` fails before its turn starts, including a usage error, it still writes the `run_end` envelope (after a pending `session` frame under `stream-json`), whose `causes` name the failure, so `stdout` is never empty on non-zero exit ([run-failure.ts](../../src/cli/run-failure.ts)).

### The `run_end` frame

Every `pancode run --output-format stream-json` stream ends with one `run_end` result envelope (`schemaVersion: 3`), and `--output-format json` writes that envelope alone, including after `--timeout` or signals ([run-json-schema-v2.ts](../../src/cli/modes/run-json-schema-v2.ts)):

```json
{"type":"run_end","schemaVersion":3,"mode":"main","runId":"...","sessionId":"...","pid":4242,"cwd":"/work/repo","pancodeVersion":"...","startedAt":"...","endedAt":"...","durationMs":8120,"exitCode":1,"outcome":"failed","outcomeDetail":"noop","causes":[{"code":"noop"}],"result":{"text":"","artifacts":[]},"verify":{"requested":0,"checks":[]},"dispatch":{"runs":[],"live":[],"undelivered":[]},"timings":{"sessionReadyMs":410,"firstRequestMs":620,"firstTokenMs":1480}}
```

`outcome` is `succeeded`, `failed`, `canceled`, `timed_out`, `previewed` (`--dry-run`) or `displayed`; `causes` lists every fact that ended the run, winner first, each as `{code, message?}` plus the payload its code names, and `outcomeDetail` is the winner's code. The winner sets `exitCode`. An absent value is an absent key: the envelope never sends `null` for an optional field. `pancode schema run-result` prints its JSON Schema.

| Field | Content |
| --- | --- |
| `mode`, `agentId` | `main`, or `agent` with the dispatched recipe id under `--agent`. |
| `runId`, `sessionId`, `parentSessionId` | The run, its session, and the session a `--fork` run branched from. |
| `pid`, `cwd`, `pancodeVersion`, `startedAt`, `endedAt`, `durationMs` | The process and its clock. |
| `result` | `text` is the answer as text mode prints it, and `artifacts` lists written artifacts. With `--output-schema`, `structured` is the validated object (exit `0` only) and `enforcedBy` is `host` or `host+provider`. |
| `route` | The `target` and `model` that answered. |
| `usage` | `main` (the run's own turn and compaction calls), `side` (side agents such as the safety judge and memory), `children` (dispatched workers) and, beside `side` or `children`, `total`; with neither, `main` is the whole run. Each scope is compact: `facts`, one fact per quantity (tokens, calls, cost), and `economy`, the display of each economy line (extra, provider charge, seat credits, energy, API equivalent), with `coverageUnknown` or `freeRuleMixed` when set. `--full-usage` writes each scope as the read model folded it instead: the call ids, every quantity's sum and `economics`, the economy projection of the same calls (extra user cost, API equivalent, seat credits, energy and the reference rows they were priced from), without period fees, which belong to a pool's period rather than a run. `dispatch.runs[].usage` follows the same choice. |
| `tools`, `safety` | `calls`, `refused` and `writes`; admission `decisions` and `blockedAttempts`, plus `judgeAllowedAttempts` when the safety judge allowed an ask. |
| `verify` | `requested` and one `checks` entry per `--verify` flag, each with `status` `passed`, `failed`, `timed_out` or `skipped` (with a `reason` of `interrupted`, `deadline` or `turn_failed`). |
| `dispatch` | `runs` (every child run the main agent dispatched, or the one sealed `RunResult` under `--agent`), `live`, `undelivered`, and `superseded`: failed runs that a later dispatch of the same task delivered, which do not fail the run. |
| `timings` | `sessionReadyMs`, `firstRequestMs` and `firstTokenMs`. |
| `limits` | Present when the run was given a limit: `requested` (`maxCostUsd`, `maxRequests`, `maxToolCalls`, `timeoutSeconds`, `requirePriced`), `enforced`, and `cost` with `--max-cost-usd`. |
| `completion` | See [Completion and `--exit-code`](#completion-and---exit-code). |
| `plan` | `--dry-run` only, with outcome `previewed`. |

Cause codes, in precedence order:

| Exit | Causes |
| --- | --- |
| signal code | `interrupted` |
| `124` | `deadline` |
| `141` | `reader_closed` |
| `2` | `unknown_flag`, `flag_conflict`, `empty_task`, `task_file_conflict`, `task_flag_conflict`, `task_authority`, `not_configured`, `schema_unsupported`, `session_live`, `io`, `not_started` |
| `5` | `unscripted` |
| `3` | `permission_required`, `judge_streak` |
| `4` | `session_cost_ceiling`, `max_cost_usd`, `autonomous_cap`, `max_requests`, `max_tool_calls` |
| `1` | `model_unavailable`, `served_model_mismatch`, `provider_error`, `context_overflow`, `no_answer`, `no_reply_text`, `missing_output`, `exploration_stalled`, `output_limit`, `schema_mismatch`, `verify_failed`, `quality_failed`, `verdict_failed`, `noop`, `limitation`, `dispatched_worker_failed`, `worker_failed`, `output_write_failed`, `run_failed` |

`not_started` covers a request refused before any work, and `run_failed` a failure no narrower code names. A `max_cost_usd` or `session_cost_ceiling` cause carries `refusal`: `reason` (`run_cost_ceiling` or `session_cost_ceiling`), `basis` (`metric: "route-price-usd"`, `scope`, `limitUsd`, and `runSpent`, this run's route-price spend, also under a session ceiling), `unknowns` (`unpricedCalls`, `unpricedRoutes`) and `remedy` (the `--max-cost-usd` flag or the `safety.limits.sessionCostUsd` setting). After a step template's turns, the sealed run record (not the envelope) keeps `stepPipeline`, which names the step tool and says whether it signalled `done`; a pipeline left unfinished keeps the outcome and carries `stoppedBy` (`cap` for the yolo continuation cap with a step still running, `unreported` when the last turn at the cap made no step call and ended on its own summary, so the step tool simply never signalled `done`, `cancel` or `failure` when a cancel or a failed turn ended it, `turn` for a turn nothing continued). Always judge overall success/failure from `run_end`, not from model-level `agent_end` ([run-json-schema.ts](../../src/cli/modes/run-json-schema.ts)).

### Completion and `--exit-code`

Once a main run settles, its `run_end` envelope carries `completion`: how the agent declared the run ended through its [`finish`](tool-usage.md#finish-declare-how-the-turn-ended) tool, never read from the answer text ([run-json-schema-v2.ts](../../src/cli/modes/run-json-schema-v2.ts)).

```json
"completion":{"declared":true,"claimed":"done","assessed":"partly_done","state":"partly_done","facts":["unvalidated_mutation"],"limitations":[],"unverified":[]}
```

`claimed` is the declared `done`, `partly_done` or `not_done`, and `assessed` is the host's reading of it: a `done` over an open obligation (`unvalidated_mutation`, `failed_check`, `uncollected_run`, `open_task`, `observation_budget` or `missing_output`, listed in `facts`) is `partly_done`. `state` is the assessment. A run that declared nothing has `declared: false`, `claimed: null` and state `unknown`. `limitations`, `unverified` and the optional `remaining` repeat the declaration.

Without `--exit-code` the completion changes no exit code. With it, a run that would exit 0 exits 1 when `state` is `partly_done` or `not_done`; `done` and an undeclared run keep 0, and every other exit is unchanged ([run-failure.ts](../../src/cli/run-failure.ts)).

### Dispatched agent output (`pancode run --agent`)

In text mode (`formatDispatchHumanOutput`, [run-output.ts](../../src/cli/run-output.ts)), `stdout` prints up to six sections in order (redacting URL credentials):

1. **Answer**: Last assistant text (prior attempts discarded on failover), or `sealedResultAnswer` when no prose was written (`mutation-report`: `summary`, `observations`, and `changed: <paths>` when `mutatedPaths` is non-empty; `scout-report` / `research-report`: `- <claim> [(<path>:<line>)|(<evidence>)]`; `world-knowledge-report`: `synthesis` and `facts`; `provenance-report`: `confirmedFacts`; `oracle-report`: `verdict`, `challenge`; fallback `output.text.trim()`). Cut-off partial output passes through `holdCutOffText`.
2. **`Failed checks:`** (optional): Failed checks of a `verifier-report` and failed `code-report` checks that ran (`ran: true`), each as `- <name>: <evidence>`. A verifier `verdict: "fail"` exits `1`.
3. **`Not verified:`** (optional): Typed unchecked items from final non-truncated sealed reports (each clipped to 400 chars): `mutation-report` (`declaredChecks`, failed `validations`), `code-report` (failed `checks` that never ran: `ran` not `true`, including reports with no `ran` field), `scout-report` (`degradedReason`, `ungroundedClaims`, ungrounded findings, `proposedSubtasks` when `needsSplit`), `world-knowledge-report` (`Discovery: unavailable|caller-supplied-only`, `uncertainties`, `followUpVerification`), `provenance-report` (`missingEvidence`, `nextInspections`), `debugger-report` (`Reproduction: unknown|not-reproduced`).
4. **`Failed: <headline>`** (optional): Shown when `receipt.exitCode !== 0` and a worker failure headline applies.
   **`Not retried: <reason>`** (optional): Why the host ran no further attempt of a failed assignment, such as an obligation unmet on an explicitly pinned route, or the retries used against `fleet.retry.maxRetries`.
5. **`Finished with a caveat: <words>`** (optional): Shown when `receipt.exitCode === 0` and calls were refused/guarded or contract conformance failed (excludes `no-tools`).
6. **`result:` summary line**:
   `result: <runId> agent=<id> exit=<n>[ verdict=<v>][ failed_checks=<N>][ verification=unverified not_verified=<N>] target=<id> model=<wireId>[ (<what served it>)][ gateway=litellm route=...] tokens=<n>[ reasoning=<n>][ error=<msg>] start=<iso> end=<iso>`
   The parenthesis appears when the run recorded its calls' upstream responses: `(1 call)` or `(<N> calls)` when every call was served by the requested model, otherwise what the providers said per call, such as `(provider reported <id> on 2 calls)` or `(no model reported on 1 call)`.

With `--output-format stream-json`, `stdout` emits NDJSON frames ([run-json-schema-v2.ts](../../src/cli/modes/run-json-schema-v2.ts)); `--output-format json` writes only the final envelope:
- `session` (`mode: "agent"`, `agentId`, `schemaVersion: 3`, `cwd`, `pancodeVersion`),
- worker events and `dispatch_scope_notice` frames (`peer_instructions_stale` warning, `worker_merged` info),
- final `run_end` envelope (`mode: "agent"`, `agentId`, the answer in words in `result.text` as text mode prints it, the sealed `RunResult` in `dispatch.runs` with any structured contract in `dispatch.runs[0].output.structured`, `notRetried` when a failed assignment ran no further attempt, and `completion` whose `limitations` include each limitation the worker recorded through its `limitation` tool); an admission refusal before any worker spawned ends with a `run_end` whose `exitCode` is `2` ([run.ts](../../src/cli/run.ts)).

Note: `--agent` refuses `--autonomy` (use `--read-only`), `--resume`, a bare `--continue`, `--fork`, `--name`, `--fail-on-noop`, `--fail-on-verify`, `--exit-code`, `--on-permission`, `--dry-run`, `--max-requests`, `--max-tool-calls`, `--verify`, `--answers`, `--output`, `--systemone`, image attachments, `--turn-mode`, `--allow-tools`, `--deny-tools`, `--delegate-tools`, and `--no-delegate` with exit `2` ([args.ts](../../src/cli/args.ts)). It accepts `--max-cost-usd`, `--output-schema`, `--worktree`, `--continue <runId>` (continue an ACP delegation in its peer's session) and `--review <run id|pancode/task/<run id>>` (run read-only in a fleet run's kept task worktree; refused with `--worktree`). With `--output-schema` the agent's sealed result contract wins ([run.ts](../../src/cli/run.ts)): a free-text recipe (`text-report`, or an ACP delegation) has its answer checked against the schema, `coder` and any other `mutation-report` recipe has the report's `summary` checked, and any other sealed-report recipe exits `2` with cause `schema_unsupported` before any model call.

### Worker permission refusals (exit 3)

Dispatched workers obey `fleet.permissions.mode` (`judge` default, `deny`, `main`, `fail`):
- Under `deny` (and denied asks under `judge` or `main`), refused calls return to the worker as tool errors (`permission denied by policy: ...`, command clipped to 200 chars).
- Reaching **3** `execute`-class policy refusals in one run exits the native or Claude SDK worker with code `3` (`WORKER_EXIT_PERMISSION_REQUIRED`), `outcome: "failed"`, `outcomeDetail: "permission_required; ..."`, and `permission refusal limit reached: the worker ended after 3 refused commands with no approval route: ...` on stderr ([worker-refusals.ts](../../src/engine/worker-refusals.ts)).
- Non-`execute` refusals and operator/timeout escalation denials do not increment the strike counter.
- `fleet.permissions.mode: fail` exits `3` immediately on the first permission denial of any class.
- Dispatch records `permission_required` in route history and blocks identical re-dispatch within the same user turn.
