PanCode / Research

The harness is
a systems problem.

A model proposes. Whether the work is right, safe and affordable is decided around it: which model gets the request, what it may touch, what it remembers, how many run at once, and who checks the result.

Operating systems answered those questions for processes. PanCode is systems software for coding agents: five subsystems that answer them in the open. Every page says what is measured and what is not.

All five subsystems are in PanCode 0.9.1. No first experiment has been run yet.

  1. 01

    Drivers: the model you have, on its own wire

    Route

    Does shaping each request for its provider wire reduce the fresh input a session pays for, and by how much on each model lineage?

  2. 02

    Memory: context as a priced storage tier

    Remember

    Does pricing an eviction against the provider's cache beat evicting by age on a long task?

  3. 03

    Scheduling: a mixed fleet under one policy

    Delegate

    Does a graded fleet finish more work per token than one agent on the same tasks?

  4. 04

    Protection: a floor at every autonomy level

    Contain

    How many approval cards can containment and a judge remove without admitting a call you would have refused?

  5. 05

    Accounting: done, checked against what ran

    Verify

    How often does a model declare a task done when the evidence does not support it, and how often does the host catch it?

I build PanCode because the model is no longer the hard part of a coding agent. What decides whether its work can be trusted is the system around it, and the questions on this page are where that system is still undecided. If you measure one of them, I will publish what you find, whatever it shows.

How each page is organized

A subsystem page opens with the design and a source map: each mechanism, the files that hold it, whether it is on by default, and the setting that turns it off. Every page then follows the same seven parts, so you can compare them and see at a glance what is still unknown.

  1. The question, stated so that an answer could turn out wrong.
  2. What is known and measured so far, with sample sizes and the build that was measured. A page says when a sample is small, when a result came from a design that no longer exists, and when nothing has been measured yet.
  3. Why the answer matters to people who use coding agents on real projects.
  4. Directions to work on: studies someone could take up, each with what to vary and measure.
  5. How to work on it today with PanCode, using only commands that exist in the stated release.
  6. A first experiment, labelled “proposed, not yet run” until someone has run it and recorded the result on the page.
  7. How to join the work.
