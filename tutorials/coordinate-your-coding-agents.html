Coordinate the coding agents you already use

Use supported coding peers for bounded assignments, distinguish managed runs from interactive handoffs, and review the results before combining them.

You can use PanCode to coordinate the coding agents you already have installed. Give a peer a focused assignment, follow a managed run where the connector supports it, and review its output before accepting the change.

Version scope

The supported peer family includes Claude Code, Codex, OpenCode, Pi, and Antigravity. Their modes and controls differ. Install and authenticate each peer's own CLI before configuring it in PanCode.

Before you start

  • PanCode with one working model connection. The first session covers it.
  • A peer's CLI installed and signed in under its own account.
  • An assignment whose answer you can check against the repository.

See which peers PanCode can use

Shell

pancode interop inspect --json
pancode configure --interop

The first command reports what PanCode can find; the second configures interoperability. In a terminal conversation, /hub interop shows the available connections. The interoperability guide covers the mode for each peer.

Choose managed work or an interactive handoff

The three commands answer different needs. Pick by whether you want a recorded run or a place to work with the peer yourself. An ACP peer is one PanCode drives over the Agent Client Protocol; a headless target runs the peer's own CLI once for the task.

Command What happens What PanCode records
/run <agent-id> <task> A configured ACP peer such as antigravity runs the task; acp:<id> names one explicitly The result and a sealed run record
/run --target <target> <agent> <task> A configured headless target runs it The result and a sealed run record
/panes peer <agent> [brief] A pane opens beside the conversation for you to work in No run record

The panes tutorial covers the pane host. Do not infer that a pane completed a task because it opened. Do not infer that a run record contains every internal reasoning step or mediates every operation inside a peer-owned loop.

Give one bounded assignment

That last sentence is a task instruction, not an enforced boundary. For an enforced one, put --read-only before the task, as in /run --read-only <agent> <task>; an option typed after the task text becomes part of the task. PanCode admits a read-only run only on a peer whose own sandbox refuses every write, and refuses it before launch on every other peer, ACP peers included.

Keep worker authority separate

A native worker, one of PanCode's own agents, inherits the main session's level inside its own permit and OS sandbox. At contained yolo, which is yolo's default, workers are dispatched as at default; at unconfined yolo a mediated worker runs the yolo way within its dispatch scope. A read-only worker stays at default.

Managed peer dispatches run at default permissions, even when the main session uses yolo, and each external agent runs its own tool loop.

A read-only run must leave every file outside PanCode's home unchanged. It is admitted only where the peer's own sandbox guarantees that, so check the peer before you rely on it.

Peer Read-only headless run
Codex Runs under its read-only sandbox mode
Claude Code Refused before launch
Antigravity Refused before launch
Pi Refused before launch
OpenCode Refused before launch

ACP peers may own their tools. Explicitly permitting peer-owned tools changes what PanCode can observe and mediate, so read the guide's permission limits before using such a peer on sensitive work. PanCode's own shell commands and native workers' commands run in an OS sandbox when one is available. External peers keep their own authority.

Separate changes with a worktree

For supported headless dispatch, --worktree keeps a Git task branch for review. That helps you compare two proposed changes without mixing their working files.

A worktree is an organizational boundary. It does not confine a peer's filesystem or network access. Keep assignments narrow, inspect the branch and diff, and run the repository's checks before merging a result.

Review before combining

What to look for

A useful result may be a diagnosis, a patch, or a failed attempt that reveals a missing dependency. Look for the files it touched, the checks it ran, and the limits of its report. A claimed test result and an observed check are different evidence.

When comparing agents, give them the same task and evaluate the actual output. Record the model, connector, setup, check results, and any costs you can substantiate. PanCode coordinating two peers does not make either one better.

Boundaries

  • Supported modes differ by peer, and some cannot receive live steering. The Antigravity CLI over ACP can.
  • A pane is an interactive handoff; it produces no run record.
  • Peer accounts, subscriptions, and usage limits stay with each peer's own provider.
